# GoPie 项目实验结果

使用 [Markdown 模板](assets/experiment-report.md) 创建或更新用户指定位置的 `<项目名>.md`。根据本次实验的产物填写报告，在已有报告中保留本次更新范围之外的内容。实验执行、重跑和清理需要由用户另行提出。

## 确认批次与覆盖

- 读 GoPie 仓库的 `AGENTS.md` 和 `docs/results-reporting.md`。确认本次原始、G 和 F 副本的 Git HEAD、实验时使用的 Go 和 GoPie 版本、日志目录、实际参数及测试范围。以运行日志和构建记录为准，信息缺失时写“待核实”。G/F 的源码行号来自各自的插桩副本，`-race` 的行号来自原始副本。
- G/F 查 `gopieRes/PROJECT_COMPLETE`、`.done/`、逐二进制日志和预期包或二进制清单。有队列状态时一并查 `state/<STEP>.done`。分别报告完成标记、预期项与已记录项、逐项退出码和实际覆盖。依据日志注明非零退出、信号中断、失败或欠采样涉及的测试包。
- 同一批次续跑时合并各段保留的证据，从逐二进制标记核对全批次状态。`PROJECT_COMPLETE` 中的 `ok`、`failed`、`resumed_skipped` 和 `elapsed` 只描述该次调用。需要报告累计耗时时汇总已核实的各段时间，并注明是否含暂停、准备和编译。单包验证等独立批次另行注明。
- `-race` 用 `summary.txt` 或 `summary.csv` 核对包日志数和通过、失败等状态，再查 `package_logs/*.json` 核实所跑轮次、提前退出和超时。记录 G、F 与基线的模块、包或测试范围差异。按仓库指南核对参数、缓存、预算及去重口径后再作比较。现有脚本的秒数按墙钟时间报告。

## 核对并记录检出

### G 和 F

- 每个模式内按缺陷类型和完整 `signature` 去重。表中可显示能区分条目的签名前缀。同一签名跨包共用编号，按包列出测试、命中次数和代表证据。访问点相同而签名不同的条目保留各自编号。
- 交叉核对 `alldatarace.txt`、`allpanic.txt` 和逐二进制日志里的 `[ORACLE REPORT]`、`WARNING: DATA RACE`、`panic:`。命中次数取对应聚合记录的 `count`。聚合缺失时用逐二进制日志补录并标出来源，缺失的聚合计数填 `—`。无法确认完整签名的证据注明待核实，唯一签名数只计已确认的记录。

### 原生 -race

- 解码 `package_logs/*.json` 的输出事件，识别完整的竞争警告块。按测试包和两侧实际访问点组成的无序对去重，每侧保留读写类型、文件行号和函数。标准库或依赖中的访问保留原栈帧，并用可定位的项目调用点区分访问场景。合并同组的可确认测试及子测试，列出去重组数和原始警告块数。`REPORT.md` 和 `summary.*` 可辅助复核，详细结果以原始日志按上述口径核算。
- 每种模式的数据竞争表保留测试包、两侧访问点、测试和代表证据。证据用日志目录下的相对路径加原文件行号或行区间，例如 `package_logs/example.json:120–168`。源码行号与日志行号分别记录。无法核实的字段标明缺失或待核实。

### Panic 和结论措辞

- 用条目记原始 panic 消息、发生点和函数、测试包、测试名及日志行区间。保留测试代码、标准库或依赖中的实际发生点。G/F 按唯一签名计数，基线可列原始记录数并明确计数单位。
- 有证据支持的环境与测试条件在本节简列，注明触发条件、数量、受影响的包和证据。原因存疑时保留观察到的现象并标注待核实。`panic: test timed out` 只计入超时欠采样，列出包和证据。
- 已核对的日志中没有命中时写“现存日志未检出”。尚未执行、日志缺失和覆盖不完整分别说明实际状态。报告提交前复核去重总数、表中编号、退出码统计和代表证据的行区间。
