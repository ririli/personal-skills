# 开发者缺陷汇报

将用户提供的错误日志和代码整理为准确、自然、可直接复制到 GitHub Issue 的报告。

## 分析依据

- 有本地源码时，检查日志涉及的函数及必要的调用关系，确认具体字段、操作和同步方式。
- 区分日志直接证明的事实、源码支持的原因和仍需验证的推测。
- 不将测试触发的问题直接认定为测试自身的缺陷；根据竞争代码的位置判断问题属于测试辅助代码还是产品实现。
- 不编造复现结果、影响范围、版本、commit、代码链接或验证结论。
- 错误日志用于理解错误现象、定位执行路径和辅助分析；生成报告时，以实际核对的原项目源码及其代码位置为准，不直接沿用日志中的路径和行号。

对于数据竞争，说明：
- 哪两个 goroutine 访问了同一个字段。
- 各自执行的是读取还是写入。
- 现有锁或同步机制为何没有覆盖这两次访问。
- 测试结束、异步停止或固定等待等行为如何触发竞争，仅在证据支持时解释。

## 插桩项目与 fuzzing 报告

部分错误日志来自插桩项目上的 fuzzing。插桩代码的设计目标是不改变原项目的业务逻辑，只影响函数或 goroutine 的调度顺序。分析时以此为背景，同时核对相关插桩是否符合这一前提。

插桩项目默认位于：
`\\wsl.localhost\Ubuntu\home\riri\realProjects`

### 分析顺序

1. 先检查插桩项目代码。根据日志中的路径、调用栈和访问位置，确认实际执行的代码、相关调用关系及插桩介入的位置，分析错误如何被触发。
2. 再检查原项目代码。将相关函数、字段访问和同步操作逐一对应回原项目，核对业务逻辑、调用关系和同步方式是否一致。不能直接沿用插桩项目的行号，也不能只凭函数同名认定代码一致。
3. 结合两份代码判断：插桩是否只是暴露了原项目中已有的执行交错，还是引入了原项目不存在的行为。重点核对相关插桩是否改变了共享状态、同步关系或 goroutine 生命周期。
4. 原项目位置、对应版本或代码映射无法确定且影响结论时，向用户询问，不猜测对应关系。

### 结论与报告

- 区分“插桩项目中已经观察到的问题”和“原项目源码支持的问题原因”。未经验证，不声称原项目已直接复现。
- 不因问题由 fuzzing 或调度干预触发，就认定它属于插桩缺陷；也不因插桩的设计目标是保持业务逻辑，就直接认定它属于原项目缺陷。
- 若相关插桩只改变调度顺序，而原项目中存在相同的冲突访问与同步缺口，应围绕原项目代码解释根因；插桩如何暴露问题仅用于分析判断，无需写入对外报告。
- 若发现插桩改变了相关逻辑或同步语义，应明确说明该差异对结论的影响；证据不足时，保留不确定性。
- 生成开发者汇报时，以对原项目源码的分析为依据，问题描述、冲突访问、原因分析及代码位置均对应原项目。
- 错误日志用于理解错误现象、定位执行路径，并辅助分析插桩项目；日志中的路径和行号不直接作为对外报告的代码位置。
- 报告中的文件路径、行号及代码链接，以实际核对的原项目代码为准。尚未完成映射时，不用插桩位置代替，也不猜测原项目位置。
- 确认缺陷是原项目固有、并非插桩引入后，对外报告无需介绍插桩项目、fuzzing 或调度干预过程；实际使用了 race 检测时，发现背景直接写“通过 race 检测发现”。这不代表已在未插桩的原项目上直接复现，不得增加此类未经验证的表述。
- 若尚不能排除插桩引入问题，先向用户说明分析中的不确定性，不按已确认的原项目缺陷撰写报告。

## 报告格式

GitHub Issue 的标题和正文分别交付：
- 标题放在独立的纯文本代码块中。
- 正文放在独立的 markdown 代码块中，方便直接复制，并保留链接括号。
- 正文中不重复标题，不包含 “Body:” 或“内容栏：”等说明文字。

标题采用：
`包或模块: 具体操作及缺陷`

正文默认包含：
1. 一句简短、自然的问候和发现背景。
2. 问题描述。
3. 竞争位置；非并发缺陷可改为“相关位置”。
4. 原因分析。
5. 以“期待得到你的回复。”结尾；英文使用“I look forward to your reply.”。

默认先用中文撰写；用户指定英语或要求翻译时使用英语。翻译应保持原意和技术细节，不擅自增加结论。

用户只需要上述内容时，不额外添加修复方案、复现步骤、环境信息或验证建议。用户要求这些内容时，根据已有证据补充。

## 语气

- 面向维护者，礼貌、自然、直接，避免公文腔和过度客套。
- 开头可以写：“大家好，我在运行 race 检测时发现了……”
- 英文可以写：“Hi everyone, I found … while running the race detector.”
- 用具体代码行为解释问题，避免指责开发者。
- 明确事实；推测使用“可能”等限定词，不用含糊措辞弱化已确认的问题。

## 代码链接

正文中的代码位置使用 Markdown 链接：
`[task/task.go:653](URL)`

用户要求自行填写链接，或没有足够信息生成准确链接时，保留空括号：
`[task/task.go:653]()`

优先使用与已核对源码对应的版本标签（如 `v1.12.0`）生成代码链接，并确认该版本下的文件内容和行号一致；不要仅因某个版本较新就使用它：
`https://github.com/owner/repo/blob/v1.12.0/path/to/file.go#L653`

没有可确认的对应版本标签时，才使用已核实的固定 commit 链接；版本标签和 commit 均无法确认时，保留空括号。不要猜测版本标签、分支或 commit 来拼接链接。

多行链接使用：
`https://github.com/owner/repo/blob/v1.12.0/path/to/file.go#L650-L655`

## 正文示例

以下示例展示结构，实际内容应根据证据调整：

Hi everyone, I found a data race in the `package` package while running the race detector. Here are the details.

### Description

Describe the trigger and the conflicting behavior.

### Conflicting Accesses

The locations below refer to the original project source code checked during analysis:

- **Write:** [path/to/file.go:100](), where `FunctionA()` updates the shared field.
- **Read:** [path/to/file.go:120](), where `FunctionB()` reads the same field without the required synchronization.

### Root Cause

Explain which access falls outside the synchronization mechanism and how the two operations can overlap.

I look forward to your reply.
